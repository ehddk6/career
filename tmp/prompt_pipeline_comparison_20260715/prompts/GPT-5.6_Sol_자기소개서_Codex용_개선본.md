# Codex용 자기소개서 독립 생성·블라인드 평가·최종 감사 시스템

## 목적

첨부된 채용공고, 직무기술서, 이력서, 경력기술서, 경험 자료와 공식 외부 자료를 바탕으로 사실에 맞고 면접에서 설명 가능한 자기소개서를 만든다.

작업은 다음 원칙을 따른다.

1. 원자료와 생성물을 분리한다.
2. 확인된 사실과 해석을 구분한다.
3. 후보를 독립적으로 생성한다.
4. 글자 수와 점수 계산은 코드로 처리한다.
5. 후보 전략과 생성 순서를 평가자에게 공개하지 않는다.
6. 합성본을 자동으로 우수하다고 보지 않는다.
7. 최종 선택은 사실 정확성, 문항 충족, 직무 연관성, 면접 방어 가능성을 우선한다.
8. 원자료를 수정하거나 덮어쓰지 않는다.

## 실행 방식

현재 작업공간을 먼저 읽기 전용으로 확인한 뒤 다음 구조를 만든다.

```text
sol_application/
├─ input/
├─ frozen/
├─ candidates/
├─ validation/
├─ judges/
├─ synthesis/
├─ comparison/
├─ final/
└─ scripts/
```

원본 파일은 `input/`에서 읽고 수정하지 않는다. 생성물은 단계별 디렉터리에 저장한다.

각 실행에는 다음 메타데이터를 부여한다.

```yaml
run_id: SOL-YYYYMMDD-HHMM
data_package_id: SOL-DATA-001
data_package_version: 1.0
frozen_at:
job_posting_date:
research_cutoff_date:
count_mode:
candidate_count: 4
```

`data_package_id`와 `data_package_version`이 다른 자료를 한 실행에서 혼용하지 않는다.

## 글자 수 기준

지원 사이트 또는 공고에서 글자 수 기준을 확인한다. 확인 결과에 따라 `count_mode`를 다음 중 하나로 설정한다.

- `WITH_SPACES_WITHOUT_LINEBREAKS`
- `WITHOUT_SPACES`
- `WITH_LINEBREAKS`
- `BYTE_BASED`
- `SITE_VERIFIED`

기준을 확인하지 못하면 임의로 하나를 확정하지 않는다. 공백 포함, 공백 제외, 줄바꿈 포함 값을 모두 계산하고 `count_mode: UNVERIFIED`로 표시한다. 기준이 불명확한 상태에서 후보를 탈락시키지 않는다.

`BYTE_BASED`는 사이트의 실제 바이트 규칙을 확인한 경우에만 사용한다.

# STEP 0. 원자료 동결과 사실 감사

## 작업

1. 입력 파일 목록과 적용 대상을 확인한다.
2. 원본 파일의 해시를 계산하고 `frozen/manifest.json`에 기록한다.
3. 기존 자기소개서는 사실 확정 근거로 단독 사용하지 않는다.
4. 기존 자기소개서의 경험, 수치, 동기, 감정, 평가 내용은 이력서, 경력기술서, 증빙 자료 또는 사용자의 직접 확인으로 교차 검증된 경우에만 확정한다.
5. 최신 외부 정보는 공식 자료를 우선해 조사하고 발표일, 기준일, 조회일과 URL을 기록한다.

## PERSONAL FACT LEDGER

다음 필드로 작성한다.

| ID | 경험·사실 | 기간 | 공식 역할 | 직접 행동 | 판단 근거 | 결과 | 수치 | 수치 산출 방식 | 개인 기여 범위 | 출처 파일·위치 | 상태 |
|---|---|---|---|---|---|---|---|---|---|---|---|

상태는 다음만 사용한다.

- `CONFIRMED`
- `NEEDS_VERIFICATION`
- `CONFLICT`
- `PROHIBITED`

원자료에 명확히 없으면 다음을 `CONFIRMED`로 처리하지 않는다.

- 행동한 이유
- 감정
- 지원동기
- 가치관
- 배운 점
- 타인의 반응이나 평가
- 팀 성과 중 개인 기여도
- 성과 수치
- 행동과 결과의 인과관계

## EXPERIENCE MAP

| 경험 ID | 증명 가능한 역량 | 가장 적합한 문항 | 대체 경험 | 재사용 가능 여부 | 재사용 시 다른 관점 | 면접 위험 |
|---|---|---|---|---|---|---|

같은 경험의 재사용은 기본적으로 피한다. 재사용이 필요한 경우 재사용 경험과 대체 경험을 다음 기준으로 비교한다.

- 문항 적합성
- 직무 연관성
- 행동 구체성
- 사실 안전성
- 면접 방어 가능성

각 항목은 5점이며 총점 차이가 3점 이내면 대체 경험을 사용한다. 재사용 경험이 4점 이상 높을 때만 재사용을 허용한다. 이 점수는 경험 배치용 내부 판단에만 사용한다.

## JOB PACKET

다음을 추출한다.

- 기관명과 직무명
- 실제 담당업무
- 주요 이해관계자
- 필수·우대 조건
- 문항 원문
- 문항별 하위 요구
- 최소·최대 글자 수
- 글자 수 계산 기준
- 평가 의도
- 입사 후 수행 가능성이 높은 행동
- 증명해야 할 역량
- 공고에 없으므로 추정하면 안 되는 업무

## RESEARCH PACKET

| ID | 검증된 주장 | 출처 기관 | 자료명 | 자료 유형 | 발표일 | 기준일 | 조회일 | URL | 페이지·표 | 적용 범위 | 본문 활용 가능 여부 |
|---|---|---|---|---|---|---|---|---|---|---|---|

최신 실적, 정책 시행 여부, 법률·규제, 자료 연계 가능 범위, 관세율, 금리, 환율, 연체율과 피해 규모는 공식 자료로 확인하지 못하면 사용하지 않는다.

## INTERVIEW DEFENSE TABLE

| 경험 ID | 직접 한 일 | 판단 근거 | 사용 도구 | 수치 산출 방식 | 팀 역할 구분 | 예상 꼬리질문 | 방어 가능 여부 |
|---|---|---|---|---|---|---|---|

수치 산출 방식이나 개인 기여 범위를 설명할 수 없으면 최종 본문에서 해당 수치를 사용하지 않는다.

## 출력 파일

```text
frozen/manifest.json
frozen/data_package.yaml
frozen/personal_fact_ledger.md
frozen/experience_map.md
frozen/job_packet.md
frozen/research_packet.md
frozen/interview_defense_table.md
frozen/needs_verification.md
frozen/prohibited_claims.md
```

자기소개서 초안이나 평가 점수는 작성하지 않는다.

# STEP 1. 독립 후보 생성

기본 후보 수는 4개다. 각 후보는 별도의 실행 컨텍스트에서 만들고 다른 후보의 내용, 순위, 평가를 보지 않는다.

공통 DATA PACKAGE는 동일하게 사용하되 경험 배치와 우선 기준을 다르게 한다.

## 후보 전략

### A. FACT_FIRST
검증된 사실, 직접 행동, 설명 가능한 결과를 최우선으로 한다. 과장 위험이 있으면 표현을 낮춘다.

### B. QUESTION_FIRST
문항의 모든 하위 질문에 직접 답하고 핵심 답을 앞에 둔다. 배경과 기관 설명을 최소화한다.

### C. EXPERIENCE_DIVERSITY
문항별 증거와 경험의 중복을 최소화한다. 대체 경험이 충분하면 같은 경험을 반복하지 않는다.

### D. JOB_RELEVANCE
경험을 실제 직무 행동과 연결한다. 입사 후 확인, 대조, 기록, 안내, 보고, 개선의 수행 순서를 구체적으로 쓴다.

후보 전략의 차이는 문체만이 아니라 경험 선택과 배치에서 드러나야 한다.

## 공통 사실 규칙

사용 금지:

- FACT LEDGER에 없는 개인 경험·행동·감정
- 확인되지 않은 수치
- 실제로 사용하지 않은 도구
- 확인되지 않은 타인의 반응과 평가
- 팀 성과를 개인 성과로 확대한 표현
- 공식 자료로 확인되지 않은 최신 정보
- 원자료에 없는 인과관계
- 사용자가 확인하지 않은 지원동기와 가치관

다음 표현은 직접 행동 근거가 있을 때만 사용한다.

- 주도했습니다
- 개선했습니다
- 해결했습니다
- 달성했습니다
- 설득했습니다
- 기여했습니다
- 효율을 높였습니다

## 문항별 작성 원칙

### 지원동기
다음을 구분해 답한다.

1. 왜 해당 직무인가
2. 왜 해당 기관인가
3. 어떤 경험과 업무 방식이 그 선택과 연결되는가
4. 무엇을 배우고 어떤 방식으로 기여할 것인가

기관명만 바꾸면 다른 기관에도 그대로 적용되는 문장을 줄인다. 확인되지 않은 개인적 인연, 어릴 때부터의 관심, 공익적 사명감, 감정적 계기를 만들지 않는다.

### 조직 적응
중요하게 생각하는 태도, 그 이유, 실제 경험, 입사 후 실천 방법을 연결한다. ‘빠르게 배우겠다’, ‘소통하겠다’만으로 끝내지 않는다.

### 업무수행계획
입사 초기 학습, 자료 처리 순서, 오류·누락 방지, 고객 안내 기준, 담당자 보고, 숙련 후 개선 방식을 중심으로 쓴다. 경험 설명보다 수행계획이 길어야 한다.

### 경제·사회 이슈
이슈, 영향 경로, 영향을 받는 기업의 구분, 우선 지원 기준, 정책금융 방안, 신속성과 건전성의 균형, 사후관리를 포함한다. 지원자가 최종 의사결정권자인 것처럼 쓰지 않는다. 공식 자료를 반복하는 데 그치지 말고 지원 직무와 현실적인 역할을 연결한다.

## 인과관계 기준

다음 흐름을 확인한다.

```text
문제 → 지원자의 판단 → 직접 행동 → 확인된 결과
```

보고서 작성, 개선안 채택, 직접 적용, 적용 후 결과는 각각 다른 단계다. 원자료에서 확인되지 않은 단계를 연결하지 않는다.

인과관계가 약하면 다음처럼 낮춘다.

- ‘향상시켰습니다’ → ‘향상된 과정에 참여했습니다’
- ‘해결했습니다’ → ‘원인을 확인하고 개선안을 제시했습니다’
- ‘비용을 절감했습니다’ → ‘비용 절감 판단에 필요한 근거를 제공했습니다’

## 문체 기준

- 정중한 경어체
- 핵심 답 선배치
- 자연스러운 한국어 어순
- 행동과 결과를 한 문장에 과도하게 넣지 않음
- 같은 종결어미와 도입·마무리 반복 최소화
- 추상어보다 실제 행동 사용
- 일부러 거칠거나 불완전한 문장으로 만들지 않음
- 기존 문체가 있으면 사실을 해치지 않는 범위에서 반영

근거 없이 사용하지 않을 표현:

- 최선을 다하겠습니다
- 열정을 발휘했습니다
- 소통의 중요성을 배웠습니다
- 협업의 가치를 깨달았습니다
- 시너지를 창출했습니다
- 귀사의 발전에 이바지하겠습니다
- 적극적으로 노력했습니다
- 누구보다 빠르게 수행했습니다

## 출력

각 후보를 다음 파일로 저장한다.

```text
candidates/candidate_A.md
candidates/candidate_B.md
candidates/candidate_C.md
candidates/candidate_D.md
```

각 파일은 문항 원문, 답변 본문, 사용한 FACT ID, 사용한 RESEARCH ID를 분리해 기록한다. 제출용 본문에는 ID를 넣지 않는다.

후보 전략명, 자체 평가, 예상 순위는 본문에 출력하지 않는다.

# STEP 2. 코드 기반 검증

`scripts/validate.py`를 작성해 다음을 계산한다.

- 공백 포함·줄바꿈 제외 글자 수
- 공백 제외 글자 수
- 줄바꿈 포함 글자 수
- 필요 시 확인된 바이트 규칙
- 최소·최대 충족 여부
- 목표 범위 충족 여부
- 문항 수와 제목 형식
- 기관명·직무명 표기 일치
- 금지 메타 태그 포함 여부

`count_mode`가 `UNVERIFIED`이면 세 계산값을 모두 출력하고 길이만으로 후보를 탈락시키지 않는다.

길이 위반 문항만 수정한다. 사실, 핵심 메시지, 경험 배치와 문체는 유지한다.

늘릴 때는 FACT LEDGER의 판단 근거, 직접 행동, 처리 순서, 직무 적용 방식만 보강한다.

줄일 때는 다음 순서로 제거한다.

1. 범용적 다짐
2. 기관 역할의 반복 설명
3. 중복 결과
4. 상황의 과도한 배경
5. 다른 기관에도 적용되는 문장

검증 결과를 `validation/candidate_validation.json`과 표 형태의 Markdown으로 저장한다.

# STEP 3. 익명화

후보 이름과 생성 순서를 무작위 ID로 바꾼다. 예: `R8`, `C3`, `M7`, `P2`.

평가 패키지에 포함:

- DATA PACKAGE ID와 버전
- FACT LEDGER
- EXPERIENCE MAP
- JOB PACKET
- RESEARCH PACKET
- INTERVIEW DEFENSE TABLE
- 문항 원문
- 코드로 계산한 글자 수
- 익명 후보

전달 금지:

- 후보 전략
- 생성 순서
- 작성 프롬프트
- 자체 설명
- 사용자 선호
- 이전 평가

매핑은 `validation/anonymization_map.json`에 저장하고 평가자에게 노출하지 않는다.

# STEP 4. 독립 심사

세 심사위원을 별도의 실행 컨텍스트에서 수행한다.

## 심사위원 역할

### RECRUITER
문항 충족, 핵심 파악, 다음 전형으로 넘길 이유, 범용성, 경험 배치를 본다.

### JOB_FACT_AUDITOR
FACT LEDGER 일치, 개인 기여와 팀 성과 구분, 직무 연결, 인과관계, 수치 설명 가능성을 본다.

### KOREAN_EDITOR
자연스러운 한국어, 번역투, 명사화, AI식 반복 구조, 지원자 말투를 본다.

## 공통 배점

| 항목 | 배점 |
|---|---:|
| 문항 요구 충족 | 20 |
| 사실 정확성·과장 방지 | 20 |
| 직무 연관성 | 15 |
| 판단·행동 구체성 | 15 |
| 경험 선택·배치 | 10 |
| 면접 방어 가능성 | 10 |
| 자연스러운 한국어 | 5 |
| 지원자 고유성 | 3 |
| 글자 수·형식 | 2 |

점수는 후보 압축을 위한 보조 자료이며 사실 오류를 상쇄하지 못한다.

## HARD FAIL 분류

### DETERMINISTIC
코드나 원자료 대조로 바로 확인 가능한 오류:

- 글자 수 제한 위반
- 기관명·직무명 오류
- 문항 누락
- 금지 메타 태그
- 존재하지 않는 FACT ID 또는 RESEARCH ID

### SEMANTIC
해석과 원자료 대조가 필요한 오류:

- 팀 성과의 개인화
- 허위 인과관계
- 면접에서 설명할 수 없는 핵심 주장
- 확인되지 않은 개인 사실
- 최신 외부 사실의 과장

심사위원 한 명이 SEMANTIC HARD FAIL을 제기했다고 즉시 탈락시키지 않는다. `REVIEW_REQUIRED`로 표시한 뒤 JOB_FACT_AUDITOR가 원자료 위치를 대조해 확정한다.

후보 탈락은 다음 경우에만 한다.

1. DETERMINISTIC HARD FAIL이 코드로 확인됨
2. JOB_FACT_AUDITOR가 출처 위치와 함께 SEMANTIC HARD FAIL을 확정함
3. 동일한 SEMANTIC 사유를 두 명 이상이 제기하고 원자료 대조로 확인됨

# STEP 5. 판정과 집계

`scripts/aggregate.py`를 작성한다.

1. DATA PACKAGE ID와 버전 일치 여부를 검사한다.
2. DETERMINISTIC HARD FAIL을 반영한다.
3. `REVIEW_REQUIRED`를 원자료와 대조해 확정·해제한다.
4. 유효 후보만 중앙값 총점, 핵심 항목 중앙값, 최저점, 최고점, 심사위원 간 편차를 계산한다.
5. 점수 차이 8점 이상은 평가 불일치로 표시한다.
6. 1위와 2위 중앙값 차이가 2점 이하면 동급으로 처리한다.
7. 점수만으로 합성 요소를 선택하지 않는다.

다른 후보의 요소는 동일 문항의 동일 요소를 심사위원 3명 중 2명 이상이 `transferable_elements`로 지목한 경우에만 합성 후보로 인정한다.

---

# STEP 6. 최소 수정 합성

전체 1위 후보를 기본안으로 유지한다. 합성 자체를 목표로 하지 않는다.

다른 후보의 요소는 다음을 모두 충족할 때만 가져온다.

1. 동일 요소를 심사위원 2명 이상이 우수하다고 지목
2. 1위 후보의 구체적 약점을 해결
3. FACT LEDGER와 일치
4. 새로운 인과관계를 만들지 않음
5. 경험 중복을 늘리지 않음
6. 글자 수 제한 충족
7. 면접 방어 가능성을 낮추지 않음
8. 문체와 논리 흐름을 해치지 않음

새로운 경험 재사용이 생기면 STEP 0의 재사용 비교를 다시 적용한다.

출력:

```text
synthesis/version_S.md
synthesis/change_log.md
synthesis/validation.json
```

변경 기록에는 문항, 기존 문제, 변경 내용, 근거 심사위원 수, FACT ID를 적는다.

1위 후보의 공통 약점이 없거나 합성 조건을 충족하는 요소가 없으면 VERSION S를 만들지 않고 기존 1위를 유지한다.

# STEP 7. 기존 1위와 VERSION S 블라인드 비교

비교 전에 두 버전 모두 사실, 문항, 길이, 기관명, 면접 방어 기준을 통과해야 한다.

두 버전을 X·Y로 무작위 배치한다. 평가자는 어느 쪽이 기존 1위인지 알 수 없어야 한다.

문항별 선택은 진단 자료로만 사용한다. 최종 제출본은 반드시 X 또는 Y 중 하나의 전체 버전을 선택한다. 문항별 우수 부분을 다시 섞지 않는다.

문항별 결과가 갈려도 전체 일관성, 경험 배치, 사실 안전성, 면접 방어 가능성을 기준으로 `overall_choice`를 정한다.

혼합본이 꼭 필요하다고 판단되면 X·Y 비교를 종료하고 별도의 VERSION Z를 만든 뒤 STEP 2, STEP 6의 사실·길이·중복 감사와 STEP 7 비교를 다시 수행한다. 감사 없이 혼합본을 제출하지 않는다.

비교 JSON:

```json
{
  "comparison_ready": true,
  "hard_fail": {
    "X": [],
    "Y": []
  },
  "question_choices": {
    "q1": {
      "choice": "X",
      "reason": "",
      "decisive_difference": ""
    }
  },
  "risk_audit": {
    "remaining_fact_risks": {
      "X": [],
      "Y": []
    },
    "interview_defense_risks": {
      "X": [],
      "Y": []
    },
    "experience_duplication": {
      "X": [],
      "Y": []
    },
    "style_regression": {
      "X": [],
      "Y": []
    }
  },
  "overall_choice": "X",
  "overall_reason": "",
  "remaining_risks": []
}
```

점수나 품질 등급은 사용하지 않는다.

# STEP 8. 최종 제출 전 감사

최종 선택본을 새 컨텍스트에서 감사한다.

검사:

- 수치, 기간, 기관명, 역할
- 개인 기여와 팀 성과
- 행동과 결과의 인과관계
- 지원동기와 가치관의 확인 여부
- 모든 하위 질문 충족
- 경험과 문장 중복
- 업무수행계획과 경험 설명의 비중
- 기관 고유성과 사실 안전성
- 최신 외부 정보의 출처와 기준일
- 정책 문항의 우선 기준, 대상 구분, 현실적 역할
- 면접에서 직접 한 일, 판단 근거, 수치 계산, 팀 역할을 설명할 수 있는지
- 번역투, 명사화, 어미 반복, 보고서 문체
- 실제 지원 사이트 기준 글자 수

HARD FAIL이 없으면 전면 재작성하지 않는다. 조사, 어미, 띄어쓰기, 주체 불명확, 반복 표현, 근거가 약한 수식어와 한두 문장의 보고서 문체만 최소 수정한다.

출력:

```text
final/final_audit.md
final/submission.md
final/submission_counts.json
final/interview_defense_notes.md
```

## 최종 제출본 형식

`final/submission.md`에는 다음만 포함한다.

- 문항 원문
- 최종 답변
- 실제 글자 수와 계산 기준

다음은 포함하지 않는다.

- 후보명
- 전략명
- 평가 점수
- 심사 의견
- 변경 기록
- FACT ID
- RESEARCH ID
- 메타 태그
- 모델 설명

## 완료 조건

다음을 모두 충족해야 완료로 보고한다.

1. 원자료가 변경되지 않음
2. DATA PACKAGE ID와 버전이 전 단계에서 일치
3. 글자 수 계산 기준이 기록됨
4. HARD FAIL이 없거나 원자료 대조로 해제됨
5. 최종본의 모든 개인 사실이 FACT LEDGER와 일치
6. 최신 외부 사실이 RESEARCH PACKET과 일치
7. 경험 중복이 허용 기준을 충족
8. 면접에서 핵심 주장과 수치를 설명할 수 있음
9. 최종 제출본에 메타 정보가 없음
10. 생성 파일과 검증 결과가 지정된 디렉터리에 저장됨
