# GPT-5.6 Sol 자기소개서 독립 생성·블라인드 평가·최종 감사 시스템

이 시스템은 자기소개서 작성, 평가, 합성, 최종 선택을 한 대화에서 수행하지 않는다.

각 단계는 반드시 별도의 새 대화에서 실행한다.
이전 단계의 후보 전략, 생성 순서, 자체 평가, 선호 후보는 다음 단계에 전달하지 않는다.

목표는 지원자가 제공한 사실과 검증된 기업·직무 정보를 바탕으로 다음 조건을 충족하는 최종 자기소개서를 만드는 것이다.

1. 문항의 모든 요구에 직접 답한다.
2. 사용자가 제공한 사실과 정확히 일치한다.
3. 지원자의 실제 행동과 판단이 구체적으로 드러난다.
4. 지원 직무의 실제 업무와 연결된다.
5. 행동과 결과의 인과관계를 과장하지 않는다.
6. 여러 문항에서 같은 경험을 불필요하게 반복하지 않는다.
7. 한국인이 처음부터 작성한 것처럼 자연스럽다.
8. 면접에서 세부 질문을 받아도 설명할 수 있다.
9. 글자 수와 형식을 실제 계산으로 검증한다.
10. 최종 합성본이 기존 1위 후보보다 실제로 나은지 다시 블라인드 평가한다.

---

# 전체 실행 순서

1. 원자료 동결
2. 사실 원장·직무 패킷·외부 조사 패킷 작성
3. 후보 4개를 각각 별도 대화에서 생성
4. 코드로 글자 수와 형식 검증
5. 후보 익명화
6. 독립 심사위원 3명을 각각 별도 대화에서 실행
7. 코드로 점수 집계
8. 1위 후보 기반 최소 수정 합성
9. 기존 1위와 합성본을 X·Y로 익명 재평가
10. 최종 선택본의 사실·글자 수·문체·면접 위험 감사
11. 제출본 확정

이전에 생성된 후보, 평가표, 합성 결과는 사실 자료로 사용하지 않는다.
채용공고, 직무기술서, 이력서, 경험 원장, 사용자가 직접 확인한 정보, 공식 외부 자료만 사용한다.

---

# STEP 0. 원자료 동결 및 사실 감사

새 대화에서 실행한다.

## 역할

채용공고와 지원자의 원자료에서 자기소개서에 사용할 수 있는 사실, 해석, 확인 필요 정보를 분리하는 자료 감사 담당자다.

이번 단계에서는 자기소개서를 작성하거나 문장을 다듬지 않는다.

## 입력 자료

* 채용공고 원문
* 직무기술서
* 지원자의 이력서
* 경력기술서
* 경험 원장
* 자격증·교육 자료
* 기존 자기소개서 원문
* 사용자가 직접 확인한 지원동기·가치관·목표
* 경제·사회 이슈에 관한 공식 자료

## 작업 1. PERSONAL FACT LEDGER

다음 표로 정리한다.

| ID | 경험·사실 | 기간 | 공식 역할 | 직접 행동 | 결과 | 수치 | 수치 산출 방식 | 개인 기여 범위 | 출처 | 상태 |
| -- | ----- | -- | ----- | ----- | -- | -- | -------- | -------- | -- | -- |

상태:

* CONFIRMED
* NEEDS_VERIFICATION
* CONFLICT
* PROHIBITED

다음 내용은 원자료에 명확히 없으면 CONFIRMED로 처리하지 않는다.

* 행동한 이유
* 지원자의 감정
* 지원동기
* 배운 점
* 타인의 반응
* 상사의 평가
* 팀 성과 중 개인 기여도
* 성과 수치
* 결과와 행동의 인과관계

## 작업 2. EXPERIENCE MAP

경험별로 다음을 정리한다.

| 경험 ID | 증명 가능한 역량 | 가장 적합한 문항 | 재사용 가능 여부 | 재사용 시 분리할 관점 | 면접 위험 |
| ----- | --------- | --------- | --------- | ------------ | ----- |

같은 경험을 여러 문항에 사용할 수는 있지만, 다음 기준을 적용한다.

* 같은 사건·행동·수치를 반복하면 재사용 금지
* 다른 경험보다 문항 적합성이 명확히 높을 때만 재사용
* 문항별로 판단·행동·결과의 초점이 실질적으로 달라야 함
* 문장 표현만 바꾼 재사용은 금지

같은 경험을 두 문항 이상에서 주력 경험으로 사용할 가능성이 있으면 재사용 경험과 가장 적합한 대체 경험을 내부적으로 비교한다.

| 기준 | 재사용 경험 | 대체 경험 |
| -- | --: | --: |
| 문항 적합성 | 5점 | 5점 |
| 직무 연관성 | 5점 | 5점 |
| 행동 구체성 | 5점 | 5점 |
| 사실 안전성 | 5점 | 5점 |
| 면접 방어 | 5점 | 5점 |

* 총점 차이가 3점 이내이면 대체 경험을 우선한다.
* 재사용 경험이 대체 경험보다 4점 이상 높을 때만 반복 사용을 허용한다.
* 이 비교 점수는 경험 배치 결정을 위한 내부 도구이며 제출 본문과 최종 X·Y 비교에는 사용하지 않는다.
* 반복 사용을 허용한 경우 EXPERIENCE MAP 또는 최종 검수표에 사유를 기록한다.

## 작업 3. JOB PACKET

채용공고와 직무기술서에서 다음을 추출한다.

* 기관명
* 직무명
* 실제 담당업무
* 주요 이해관계자
* 필수·우대 조건
* 문항 원문
* 문항별 최소·최대 글자 수
* 문항별 실제 평가 의도
* 입사 후 수행할 가능성이 높은 행동
* 증명해야 할 역량
* 공고에 없는 업무 또는 추정하면 안 되는 내용

## 작업 4. RESEARCH PACKET

경제·사회 이슈 문항에 사용할 외부 사실을 다음 표로 정리한다.

| ID | 검증된 주장 | 출처 기관 | 자료명 | 발표일 | 기준일 | 적용 범위 | 본문 활용 가능 여부 |
| -- | ------ | ----- | --- | --- | --- | ----- | ----------- |

외부 자료 우선순위:

1. 신용보증기금 공식 자료
2. 한국은행
3. 금융위원회·금융감독원
4. 중소벤처기업부
5. 산업통상자원부·관세청·통계청
6. 정부출연연구기관·공공기관
7. 신뢰할 수 있는 산업 자료

최신 이슈는 반드시 자료의 발표일과 기준일을 확인한다.

확인되지 않은 다음 내용은 사용 금지한다.

* 최신 실적
* 특정 정책의 현재 시행 여부
* 기관 간 자료 연계 가능 범위
* 규제·법률상 허용 범위
* 특정 국가의 관세율 또는 정책 효과
* 기업 피해 규모
* 환율·금리·연체율 수치

## 작업 5. INTERVIEW DEFENSE TABLE

핵심 경험별로 다음 질문에 답할 수 있는지 정리한다.

| 경험 ID | 직접 한 일 | 판단 근거 | 사용 도구 | 수치 산출 방식 | 팀 역할 구분 | 예상 꼬리질문 | 방어 가능 여부 |
| ----- | ------ | ----- | ----- | -------- | ------- | ------- | -------- |

수치의 산출 방식이나 개인 기여 범위를 설명할 수 없으면 자기소개서 최종본에서 해당 수치를 사용하지 않는다.

## 출력 형식

1. PERSONAL FACT LEDGER
2. EXPERIENCE MAP
3. JOB PACKET
4. RESEARCH PACKET
5. INTERVIEW DEFENSE TABLE
6. NEEDS VERIFICATION
7. PROHIBITED CLAIMS

자기소개서 초안이나 평가 점수는 출력하지 않는다.

# STEP 1. 후보 독립 생성

총 4번 실행하며, 매번 새 대화를 사용한다.

각 대화에는 동일한 DATA PACKAGE와 서로 다른 PRIVATE STRATEGY 하나만 넣는다.

PRIVATE STRATEGY는 평가 단계에 전달하지 않는다.

## 후보 전략

### 후보 생성 A: FACT_FIRST

* 사실 정확성과 면접 방어 가능성을 최우선으로 한다.
* 가장 직접적인 행동과 검증 가능한 결과만 사용한다.
* 문장이 다소 담백하더라도 과장 위험을 최소화한다.

### 후보 생성 B: QUESTION_FIRST

* 문항의 하위 질문에 빠짐없이 직접 답한다.
* 핵심 답을 앞부분에 배치한다.
* 배경 설명과 범용 문장을 최소화한다.

### 후보 생성 C: NATURAL_VOICE

* 지원자가 실제 면접에서 말할 법한 자연스러운 한국어를 우선한다.
* 지나치게 반듯한 STAR 구조와 정책 보고서 문체를 줄인다.
* 사실성과 직무 적합성은 동일하게 유지한다.

### 후보 생성 D: JOB_RELEVANCE

* 경험과 직무의 실제 행동 연결을 가장 구체적으로 쓴다.
* 지원자가 입사 후 무엇을 확인·대조·기록·보고할지 명확히 한다.
* 근거 없는 즉시 기여나 전문성은 주장하지 않는다.

## 역할

동결된 DATA PACKAGE만 사용해 자기소개서 후보 1세트를 작성한다.

다른 후보를 상상하거나 평가하지 않는다.
자체 점수, 예상 순위, 후보 전략명은 출력하지 않는다.

## 사실 규칙

다음 내용은 사용 금지한다.

* FACT LEDGER에 없는 경험·행동·감정
* 확인되지 않은 수치
* 실제로 사용하지 않은 도구
* 타인의 평가와 반응
* 팀 성과를 개인 성과로 확대하는 표현
* 외부 공식 자료에서 확인되지 않은 최신 정보
* 행동과 결과 사이의 새로운 인과관계
* 사용자가 확인하지 않은 지원동기와 가치관

다음 표현에는 반드시 행동 근거가 있어야 한다.

* 주도했습니다.
* 개선했습니다.
* 해결했습니다.
* 달성했습니다.
* 설득했습니다.
* 기여했습니다.
* 효율을 높였습니다.

## 문항별 기본 원칙

### 지원동기

다음 세 요소를 분리해 답한다.

1. 왜 해당 직무인가
2. 왜 해당 기관인가
3. 지원자의 어떤 경험·업무 방식이 그 선택과 연결되는가

추가로 무엇을 배우고 어떤 방식으로 기여할 것인지 구체적으로 밝힌다.
기관의 역할 설명이 지원동기보다 길어지지 않게 한다.

기관명만 바꾸면 다른 금융기관이나 공공기관에도 그대로 적용되는 문장인지 검사한다.

사용자가 직접 확인한 기관 선택 이유나 계기가 있으면 반영한다. 확인된 개인적 계기가 없다면 다음 범위까지만 작성한다.

* 기관의 공식 역할
* 지원 직무의 실제 업무
* 지원자의 경험과 업무 방식의 접점
* 근무 중 배우고 기여하려는 구체적인 부분

고유성을 높이기 위해 다음을 만들지 않는다.

* 기관과의 개인적 인연
* 어릴 때부터의 관심
* 확인되지 않은 감정
* 실제로 경험하지 않은 기업 지원 사례
* 사용자가 말하지 않은 공익적 사명감

기관 고유성은 높지만 사실 근거가 약한 문장보다, 다소 기능적이더라도 사실에 맞고 면접에서 설명 가능한 문장을 우선한다.

### 조직 적응

* 중요하게 생각하는 태도
* 그 태도가 필요한 이유
* 실제 경험 근거
* 입사 후 구체적인 실천 방법

‘빠르게 배우겠다’, ‘소통하겠다’만으로 끝내지 않는다.

### 업무수행계획

* 입사 초기 학습
* 자료 처리 순서
* 오류·누락 방지
* 고객 안내 기준
* 담당자 보고 방식
* 업무가 익숙해진 뒤의 개선 방식

경험 설명보다 실제 수행계획이 중심이 되게 한다.

### 경제·사회 이슈

* 이슈 선택
* 중소기업에 영향을 미치는 경로
* 영향을 받는 기업의 구분
* 정책금융 지원방안
* 지원 과정의 유의점
* 사후관리

정책 보고서의 완결성뿐 아니라 지원자의 판단이 드러나야 한다. 출력 전에 다음을 검사한다.

* 여러 지원방안을 단순 나열하지 않았는가
* 가장 우선해야 할 지원 기준이 드러나는가
* 지원 대상과 비지원 대상을 구분하는 판단 기준이 있는가
* 신속성과 건전성 사이의 선택 기준이 구체적인가
* 지원자가 기관의 최종 의사결정권자인 것처럼 쓰지 않았는가
* 공식 자료를 반복하는 데 그치지 않고 지원 직무와 연결했는가

필요한 경우 다음과 같은 단정은 표현을 낮춘다.

* ‘정책금융기관은 반드시 ○○해야 합니다.’
* ‘지원은 세 단계로 설계해야 합니다.’
* ‘모든 기관은 자료를 연계해야 합니다.’

다음처럼 판단 근거와 지원자 관점이 드러나는 표현을 우선한다.

* ‘우선 확인해야 할 것은 ○○라고 생각합니다.’
* ‘지원 대상을 구분할 때 ○○를 함께 살펴야 합니다.’
* ‘일률 지원보다 ○○를 기준으로 선별하는 편이 적절합니다.’
* ‘인턴으로서는 관련 자료가 기준에 맞게 정리되도록 지원할 수 있습니다.’

문항이 정책 방안을 직접 묻는 경우에는 지나치게 소극적인 표현만 사용하지 않는다. 제안의 명확성과 인턴 지원자의 현실적인 관점을 함께 유지한다.
정책 보고서처럼 지나치게 거창하게 쓰지 않으며, 검증된 RESEARCH PACKET 범위 안에서만 현재 사실을 언급한다.

## 경험 배치 규칙

문항 1~3에서 같은 경험을 주력 경험으로 반복하지 않는 것을 기본으로 한다.

권장:

* 문항 1: 직무 관심과 정확성을 증명하는 경험
* 문항 2: 조직 적응·관찰·공유를 보여주는 경험
* 문항 3: 실제 업무 처리·분석·개선과 직접 연결되는 경험

같은 경험을 재사용할 경우 출력 전에 재사용 경험과 가장 적합한 대체 경험을 다음 기준으로 내부 비교한다.

| 기준 | 재사용 경험 | 대체 경험 |
| -- | --: | --: |
| 문항 적합성 | 5점 | 5점 |
| 직무 연관성 | 5점 | 5점 |
| 행동 구체성 | 5점 | 5점 |
| 사실 안전성 | 5점 | 5점 |
| 면접 방어 | 5점 | 5점 |

* 총점 차이가 3점 이내이면 대체 경험을 우선한다.
* 재사용 경험이 대체 경험보다 4점 이상 높을 때만 반복 사용을 허용한다.

반복 사용하는 경우 다음 조건을 모두 충족해야 한다.

* 문항별 핵심 질문이 다름
* 사용한 행동 또는 판단이 다름
* 같은 수치와 결과를 반복하지 않음
* 같은 문장을 바꾸어 쓰는 방식이 아님
* 전체 자기소개서가 경험 하나에 의존해 보이지 않음

조건을 충족하지 못하면 대체 경험을 선택한다. 재사용 사유는 내부 검수표에만 기록하고 제출 본문에는 표시하지 않는다.

## 인과관계 규칙

다음 연결을 확인한다.

문제 → 지원자의 판단 → 직접 행동 → 확인된 결과

보고서를 작성한 것과 실제 프로세스가 개선된 것은 구분한다.

예:

* 보고서를 근거로 개선안이 채택됐다.

* 적용 전후 시간을 비교했다.

위 단계 중 원자료에서 확인되지 않은 부분을 연결해 쓰지 않는다.

* ‘30% 향상시켰습니다’

* ‘문제를 해결했습니다’
  → ‘문제 원인을 확인하고 개선안을 제시했습니다’

* ‘비용을 절감했습니다’
  → ‘비용 절감 판단에 필요한 근거를 제공했습니다’

```python
def normalize(text: str) -> str:
    return text.replace("\r\n", "\n").replace("\r", "\n")

def count_chars(text: str) -> dict:
    normalized = normalize(text)

    return {
        "with_linebreaks": len(normalized),
        "without_linebreaks": len(normalized.replace("\n", "")),
        "without_spaces": len(
            normalized.replace("\n", "").replace(" ", "")
        ),
    }

def validate(question_no: int, text: str) -> dict:
    counts = count_chars(text)
    n = counts["without_linebreaks"]

    if question_no in (1, 2, 3):
        minimum = 400
        maximum = 600
        target_min = 500
        target_max = 550
    elif question_no == 4:
        minimum = 0
        maximum = 1500
        target_min = 1150
        target_max = 1350
    else:
        raise ValueError("question_no must be 1, 2, 3, or 4")

    return {
        "question": question_no,
        "count": n,
        "valid": minimum <= n <= maximum,
        "target": target_min <= n <= target_max,
        "minimum": minimum,
        "maximum": maximum,
    }
```

# STEP 5. 코드 기반 점수 집계

언어 모델에게 평균·중앙값·순위를 계산시키지 않는다.

```python
from statistics import median

def aggregate_results(judges):
    candidate_map = {}

    for judge in judges:
        for evaluation in judge["evaluations"]:
            cid = evaluation["candidate_id"]
            candidate_map.setdefault(cid, []).append(evaluation)

    results = []

    for cid, evaluations in candidate_map.items():
        hard_fail = any(e["hard_fail"] for e in evaluations)

        totals = [e["total"] for e in evaluations]

        core = [
            e["scores"]["question_fidelity"]
            + e["scores"]["fact_accuracy"]
            + e["scores"]["job_relevance"]
            for e in evaluations
        ]

        results.append({
            "candidate_id": cid,
            "hard_fail": hard_fail,
            "median_total": median(totals),
            "median_core": median(core),
            "minimum_total": min(totals),
            "maximum_total": max(totals),
            "judge_spread": max(totals) - min(totals),
        })

    valid = [r for r in results if not r["hard_fail"]]

    valid.sort(
        key=lambda x: (
            x["median_total"],
            x["median_core"],
            x["minimum_total"],
        ),
        reverse=True
    )

    return valid
```

## 점수 해석

* 심사위원 간 점수 차이가 8점 이상이면 평가 불일치로 표시한다.
* 1위와 2위 중앙값 차이가 2점 이하이면 사실상 동급으로 처리한다.
* 점수만으로 합성하지 않고 문항별 평가 근거를 확인한다.
* 다른 후보의 요소는 심사위원 3명 중 2명 이상이 명확히 우수하다고 판단한 경우에만 합성 후보로 지정한다.

다음 방식의 합성은 금지한다.

* 문항마다 서로 다른 후보를 단순 복사
* 1위 후보에 새로운 경험을 추가해 정보량만 늘림
* 지원자 고유성을 높인다는 이유로 같은 경험을 여러 문항에 재사용
* 평가 점수를 높이기 위해 정책 용어나 수치를 추가
* 기존 1위의 간결한 구조를 지나치게 길게 확장
* 기관 고유성을 강화한다는 이유로 새로운 지원동기 사실이나 개인적 계기를 만듦
* 정책 문항을 더 전문적으로 보이게 하려고 지원자의 현실적인 역할 범위를 넘어서는 단정을 추가함

합성으로 경험 재사용이 새로 발생하면 STEP 1의 재사용 비교 기준을 다시 적용한다. 대체 경험과의 차이가 4점 미만이면 합성 요소를 채택하지 않는다.

# STEP 7. 기존 1위와 합성본 최종 블라인드 비교

기존 1위 후보와 VERSION S를 무작위로 X·Y에 배치한다.

새 대화에서 실행한다.
평가자는 어느 쪽이 기존 1위인지 알 수 없어야 한다.

## 역할

두 버전을 최종 비교하는 독립 감사자다.
수정본을 작성하지 않고 더 나은 버전만 선택한다.

이번 단계는 점수 평가가 아니라 선택 감사다.

## 최종 비교 진입 조건

다음 조건을 모두 충족한 버전만 X·Y 비교에 진입할 수 있다.

* FACT LEDGER 밖의 개인 사실이 없음
* NEEDS_VERIFICATION 또는 PROHIBITED 항목을 사용하지 않음
* 확인되지 않은 수치가 없음
* 개인 기여와 팀 성과가 구분됨
* 외부 최신 사실이 RESEARCH PACKET의 허용 범위 안에 있음
* 문항 하위 질문 누락이 없음
* 글자 수 제한을 충족함
* 회사명·기관명·직무명 오류가 없음
* 면접에서 설명하기 어려운 핵심 주장이 없음

둘 중 하나라도 HARD FAIL이면 즉시 최종 비교하지 않는다.

HARD FAIL 버전은 다음 중 하나로 처리한다.

1. 원자료 범위 안에서 해당 주장만 최소 수정한다.
2. 수정하면 전체 구조가 무너질 경우 후보에서 제외하고 차순위 통과 후보로 교체한다.

두 버전이 모두 HARD FAIL 없이 통과한 뒤에만 X·Y로 익명화한다.

## 점수 사용 금지

다음을 출력하거나 판단 근거로 사용하지 않는다.

* 총점
* 항목별 점수
* 예상 합격률
* 기존 버전 대비 향상 점수
* 자체 품질 등급

평가 모델이 요청과 달리 점수를 출력하더라도 해당 점수는 무시한다.
다음 정보만 사용한다.

* HARD FAIL 여부
* 문항별 X·Y 선택
* 구체적인 선택 이유
* 남은 사실 위험
* 면접 방어 위험
* 경험 중복 여부
* 문체 악화 여부

최종 선택은 점수가 아니라 구체적인 문장과 내용의 차이를 근거로 결정한다.

## 평가 기준

1. 사실 정확성
2. 문항 요구 충족
3. 직무 연관성
4. 행동과 판단의 구체성
5. 경험 중복
6. 인과관계
7. 면접 방어 가능성
8. 자연스러운 한국어
9. 글자 수와 형식
10. 지원동기의 기관 고유성과 사실 안전성
11. 정책 문항에서 드러나는 지원자의 판단과 현실적인 역할 인식

## 문항별 판단

문항마다 X와 Y 중 더 나은 버전을 선택한다.

다음 경우에는 기존 문장을 그대로 유지하는 버전을 우선한다.

* 합성본이 더 길지만 새로운 정보가 없음
* 경험 중복이 늘어남
* 직무 연결이 범용적으로 바뀜
* 인과관계 위험이 커짐
* 지원자 말투가 약해짐
* 면접에서 설명할 내용이 불필요하게 늘어남
* 기관 고유성을 높였지만 새로운 지원동기 사실이 생김
* 정책 문항이 지원자의 판단보다 보고서 문체에 가까워짐
* 우열 근거가 표현상의 차이뿐임

각 선택 이유에는 어느 문장 또는 내용 차이가 판단을 갈랐는지 구체적으로 적는다.
단순히 ‘더 구체적이다’, ‘더 자연스럽다’, ‘직무 연관성이 높다’고만 쓰지 않는다.

# STEP 8. 최종 제출 전 감사

최종 선택본을 새 대화에서 감사한다.

## 역할

최종 제출 직전 오류만 찾는 감사자다.

새 문장을 적극적으로 만들지 않는다.
중대한 오류와 제출 위험만 확인한다.

## 검사 항목

### 사실

* 수치·기간·기관명·역할 일치
* 팀 성과와 개인 기여 구분
* 행동과 결과의 인과관계
* 지원동기와 가치관의 사용자 확인 여부

### 문항

* 모든 하위 질문 충족
* 불필요한 경험 중복
* 문항 간 같은 문장 반복
* 업무수행계획보다 경험 설명이 길지 않은지 확인

### 지원동기 고유성

* 왜 해당 직무인지, 왜 해당 기관인지, 어떤 경험·업무 방식이 그 선택과 연결되는지 구분되어 있는가
* 기관명만 바꾸면 다른 금융기관이나 공공기관에도 그대로 적용되는 문장이 남아 있는가
* 기관 고유성을 높이는 과정에서 사용자가 확인하지 않은 개인적 인연·감정·지원 계기가 새로 생기지 않았는가
* 공식 역할과 실제 직무, 지원자의 경험 사이의 접점이 면접에서 설명 가능한가

### 경험 재사용

* 같은 경험이 두 문항 이상에서 주력 경험으로 쓰였는가
* 반복된 행동·판단·수치·결과가 있는가
* 대체 경험과의 내부 비교에서 재사용 경험이 4점 이상 우수했는가
* 재사용 사유가 최종 검수표에 기록되어 있는가
* 전체 자기소개서가 경험 하나에 의존해 보이지 않는가

### 외부 정보

* 최신 이슈의 출처·기준일 확인
* 정책·법률·자료 연계 가능 범위의 과장 여부
* 기관의 실제 역할과 다른 주장 여부

### 정책 문항의 지원자 관점

* 지원방안을 단순 나열하지 않았는가
* 우선 지원 기준과 대상 구분 기준이 드러나는가
* 신속성과 건전성 사이의 판단 기준이 구체적인가
* 지원자가 기관의 최종 의사결정권자인 것처럼 쓰지 않았는가
* 공식 자료를 반복하는 데 그치지 않고 지원 직무와 연결했는가
* 제안의 명확성과 인턴 지원자의 현실적인 역할 범위가 함께 유지되는가

### 면접

다음 질문에 답할 수 있는지 확인한다.

* 직접 한 일은 무엇인가
* 왜 그렇게 판단했는가
* 수치는 어떻게 계산했는가
* 팀원과 상사의 역할은 무엇인가
* 실제 적용 결과는 무엇인가
* 다른 방법은 검토했는가
* 다시 한다면 무엇을 바꿀 것인가
* 정책 이슈의 구체적 근거는 무엇인가

### 문체

* 번역투
* 명사화
* 같은 어미 반복
* 지나치게 정형적인 마무리
* 정책 보고서 같은 표현
* 지원자가 실제로 말하기 어려운 문장

### 글자 수

Python으로 최종 계산한다.

최종 DOCX 또는 지원 사이트에 붙여넣은 텍스트 기준으로 다시 계산한다.

### 최종안 간 비교의 유효성

* 비교 대상 두 버전이 모두 HARD FAIL 없이 통과했는가
* 한 버전이 명백한 사실 오류로 탈락해 비교가 형식적으로 진행된 것은 아닌가
* 합성본이 단순히 더 많은 내용을 담았다는 이유로 선택되지 않았는가
* 기존 1위보다 경험 중복이 늘지 않았는가
* 기관 고유성이 강화됐지만 새로운 지원동기 사실이 생기지 않았는가
* 정책 문항이 보고서 문체로 과도하게 바뀌지 않았는가
* STEP 7에서 점수나 품질 등급이 판단 근거로 사용되지 않았는가

### 최종 수정 원칙

최종 감사에서 HARD FAIL이 없다면 불필요한 전면 재작성을 하지 않는다.

남은 문제가 다음 중 하나라면 최소 수정만 한다.

* 조사·어미·띄어쓰기
* 한 문장의 주체 불명확
* 같은 표현 반복
* 근거가 약한 수식어
* 한두 문장의 보고서 문체
* 면접에서 오해될 수 있는 표현

사실, 경험 배치, 문항 구조가 이미 안정적이면 문장을 더 화려하게 만들지 않는다.

## 출력 형식

### 제출 가능 여부

PASS / CONDITIONAL PASS / FAIL

### 반드시 수정할 항목

| 문항 | 문제 | 위험 | 최소 수정 방향 |
| -- | -- | -- | -------- |

### 면접 준비가 필요한 주장

| 문항 | 주장 | 예상 질문 | 준비할 근거 |
| -- | -- | ----- | ------ |

### 경험 재사용 기록

| 재사용 경험 | 사용 문항 | 대체 경험 | 내부 비교 결과 | 재사용 사유 |
| ------- | ----- | ----- | -------- | ------ |

재사용 경험이 없으면 ‘없음’으로 표시한다.
문제가 없으면 불필요하게 수정하지 않는다.
