# Career Pipeline 프롬프트 통합 구현 보고서

## 결론

기존 Career Pipeline의 사실 원장·공고 고정·결정론적 검증·4후보 블라인드 심사는 유지한다. 업로드된 프롬프트를 한 개의 거대한 지시문으로 붙이는 대신, 현재 코드가 검증할 수 없는 회사조사와 면접 준비를 두 개의 JSON 계약으로 구조화해 `prepare → research/interview → finalize → rigorous selection → audit` 흐름에 연결한다.

통합 후 역할은 다음과 같이 나뉜다.

- 자기소개서 생성·선택: 기존 `rigorous_selection.py`가 담당한다.
- 회사조사 품질: `04_기업직무조사.json`이 법인, 출처 계층, 주장 상태, 사업모델, 전략 실행, 재무·경쟁·문화 분석, 직무 연결, 지원 판단을 고정한다.
- 면접 방어력: `08_면접대비팩.json`이 제출 주장, 문서 일관성, 역량, 경험 방어 깊이, 질문 티어, 답변 카드, 추가질문, 역질문, 모의면접 정책을 고정한다.
- 통합 검증: `13_프롬프트통합검증.json`이 HARD FAIL과 REVIEW REQUIRED를 분리한다.
- 후보 생성: 검증을 통과한 안전한 회사 claim과 D3/D4 이상 경험만 Sol 후보·심사 컨텍스트에 전달한다.

## 발견한 코드 결함

`rigorous_selection.py`의 최종 비교 JSON 스키마가 `q1`~`q4`를 고정 필드로 요구한다. 공고 문항이 3개 또는 5개면 실제 문항 집합과 스키마가 어긋난다. 또한 현재 스키마는 문항별 선택을 `X`/`Y` 문자열로만 받지만, 프롬프트는 선택 이유와 결정적 차이를 요구한다.

수정안은 다음과 같다.

1. JSON 스키마에서 `question_choices`를 동적 객체로 받는다.
2. 실행 시 실제 `Question.index` 집합과 정확히 일치하는지 코드로 검증한다.
3. 각 문항에 `choice`, `reason`, `decisive_difference`를 필수로 한다.
4. 사실, 면접 방어, 경험 중복, 문체 회귀 위험을 X/Y별로 분리한다.

## 새 계약의 차단 규칙

### 회사조사 HARD FAIL

- 대상 법인·target 불일치
- 출처 ID·회사 claim·공식 research claim 참조 오류
- 회사의 주장을 객관적 사실로 저장
- 사용 금지 상태 claim을 자기소개서·면접에 사용
- 사업모델 핵심 필드 누락
- 실행 단계에 비해 근거가 없는 전략
- 공고에 없는 권한을 직무 행동으로 확정
- 확정 원장에 없는 경험·claim과 회사 요구 연결
- 외부 문서의 지시문이 회사 claim에 혼입

### 면접 HARD FAIL

- 최종 자기소개서의 경험·claim·research 참조가 제출 주장 감사에 누락
- 수치 경험의 방어 깊이가 D4 미만
- 핵심 경험의 방어 깊이가 D3 미만
- TIER 1 필수 영역 누락
- TIER 1 답변 카드 누락
- 추가질문 방향이 5개 미만
- 핵심 답변에 WEAK·CONFLICT·UNKNOWN probe 존재
- 문서 충돌이 있는데 대응 전략 없음
- 모의면접이 질문을 한 번에 하나씩 제시하지 않음

### REVIEW REQUIRED

자료가 없다고 사실을 만드는 대신 다음은 검토 상태로 남긴다.

- 법인 관계 미확인
- 재무·경쟁·문화 분석에 충분한 공개 자료 없음
- 면접 단계·면접관·시간 미확인
- 회사의 가장 강한 반대 논리 또는 핵심 불확실성 부족
- 역질문 수와 질문 세트가 권장 범위보다 적음

## 실행 흐름

```text
prepare
→ contracts init
→ 회사조사·면접 JSON 작성
→ contracts validate
→ finalize --selection-mode rigorous
→ 계약의 safe claims와 defensible experiences를 후보 생성에 주입
→ X/Y 최종 비교
→ 선택본 기준 계약 재검증
→ 최종 자기소개서·면접팩·통합검증 report 고정
```

기존 실행 디렉터리에 두 JSON이 모두 없으면 이전 동작을 유지한다. 하나만 존재하면 자료 혼용을 막기 위해 차단한다. 두 파일이 존재하면 최종화 전에 검증하고, rigorous 선택 후 선택본의 근거가 면접 패킷과 다시 일치하는지 확인한다.

## 의도적으로 통합하지 않은 규칙

- 미확인 글자 수 기준으로 후보를 통과시키는 규칙: 실제 공고와 불일치하면 차단하는 현재 정책이 더 안전하다.
- Patina AI 점수를 품질 지표로 사용하는 규칙: AI 탐지 점수는 작성 품질과 동일하지 않으므로 legacy opt-in만 유지한다.
- 모든 단계에서 무조건 모델 호출: 자연스러운 초안은 후처리 호출을 건너뛰고, rigorous 선택은 명시적으로 선택했을 때만 실행한다.
- 면접 답변 전체 원고 암기: JSON에는 첫 문장·판단 기준·직접 행동·한계·직무 연결과 probe 방어만 고정한다.
- 회사 후기 하나로 조직문화를 확정: 표본 범위와 한계를 요구하고, 근거 부족은 `INSUFFICIENT_EVIDENCE`로 남긴다.

## 검증 결과

새 `prompt_contracts.py`에 대해 다음 7개 단위 테스트를 실행했다.

1. 계약 파일이 없으면 기존 실행과 호환
2. 한쪽 JSON만 있으면 fail closed
3. 템플릿 비파괴 초기화 및 DATA PACKAGE 일치
4. 완성 계약 통과 및 금지 claim의 모델 컨텍스트 제외
5. 수치 경험 D4 강제
6. 회사 claim의 prompt injection 차단
7. 실제 문항 수에 따른 X/Y 비교 검증

실행 결과: `7 passed`.

전체 저장소 테스트는 현재 실행 환경에서 GitHub 저장소를 로컬로 복제할 수 없어 실행하지 못했다. 원격 저장소에는 변경을 쓰지 않았다.
