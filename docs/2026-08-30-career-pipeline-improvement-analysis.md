# 취업 파이프라인 구조 개선 분석

작성일: 2026-08-30
대상 체크아웃: `career-nrs-shadow-pilot` / `agent/nrs-shadow-benchmark` / `f11d495b1630155f81d97de94502ded0f4fcba36`

## 결론

이 프로젝트의 다음 과제는 새로운 작성 알고리즘을 추가하는 일이 아니다. **이미 구현된 공고 분석, 자료조사, NRS, 면접지능, 감사를 실제 사용자가 한 경로로 실행하게 만드는 운영 수렴**이 최우선이다.

현재 프로젝트는 사실 권한과 검증 측면에서 상당히 깊다. 반면 입력 생성과 단계 연결이 분리되어 있어 정교한 하위 시스템이 실제 실행에서 사용되지 않는다. 로컬 과거 실행 68건 중 최신 산출물인 `05_NRS_서사선택.json`, `08_면접지능설계.json`, `13_골든패스.json`, `14_시스템불변성벤치마크.json`은 모두 0건이었다. 이는 기능이 없다는 뜻이 아니라 **운영 진입점과 마이그레이션이 부재해 채택되지 않았다는 뜻**이다.

따라서 우선순위는 다음과 같다.

1. 단일 골든패스 CLI와 기존 실행 진단/마이그레이션
2. 승인된 지원자 사실과 구조화된 공고 자격요건을 잇는 자격검증 입력 컴파일러
3. 공식 자료조사의 수집·스냅샷·주장 후보 승인을 잇는 작업 큐
4. 최종 자기소개서에서 면접 방어팩을 자동 생성하는 단일 면접 단계
5. 실제 사용 수정·선호·면접 평가를 연결하는 평가 원장과 시스템 벤치마크

## 분석 범위와 근거 수준

직접 조사한 영역은 다음과 같다.

- 코드: `career_pipeline/`의 공고, 프로필, 자격, 연구, 작성, 면접, 골든패스, 감사, 벤치마크 경로
- 테스트: 관련 테스트 파일과 전체 테스트 구조
- 문서: 기존 아키텍처 검토, 골든패스, 연구, evidence-to-signal, NRS 기본 전환 문서
- 실제 운영 표본: `취업/career_runs`의 `run.json`이 있는 68개 폴더

아래 코드 관련 결론은 현재 로컬 체크아웃에서 직접 확인한 `관찰됨` 상태다. 과거 실행 수치는 `n=68` 로컬 표본의 관찰값이며, 일반적인 취업 성공률이나 외부 사용자 행동으로 일반화하지 않는다.

## 현재 프로젝트의 강점

### 1. 사실 권한이 단계별로 보존된다

경험 원장은 확정 주장과 근거를 연결하고, 수치 주장에는 검증 방법·범위·기여도를 요구한다. 연구 정보는 지원자 경험의 근거로 승격되지 않으며, 최종 답변은 사용한 경험 주장과 연구 주장 ID를 반환한다. NRS v2도 이 권한 계약을 유지한다.

### 2. NRS v2는 실제 자기소개서 장르 문제를 해결하는 방향으로 바뀌었다

NRS v2는 검증 제약을 본문에 노출하지 않고, 허용 사실·행위자·결과·직무 연결만 산문 생성에 전달한다. 후보마다 사실·행위자·장르 게이트를 통과시키고, 여러 서사 순서를 blind 방식으로 비교한다. 사용자 승인에 따라 현재 기본 작성 전략은 `nrs_v2`이며, 실패 시 `deep_route`로 제한적으로 대체된다.

### 3. 면접지능은 단순 예상질문 목록보다 발전돼 있다

최종 자기소개서의 주장 그래프, 공식 연구, 지원자 경험을 기반으로 고정 질문과 적응형 꼬리·압박 질문을 만든다. 평가 결과는 원답변을 장기 저장하지 않고 집계된 약점만 프로필에 반영한다. 합격 확률을 추정하지 않는 경계도 명시돼 있다.

### 4. 골든패스는 변경 감지와 하위 산출물 신선도를 다룬다

연구, 작성, 면접, 최종본, 감사 단계가 SHA 기반으로 연결된다. 최종본이 바뀌었는데 면접팩이 그대로면 완료를 막는 등, 오래된 하위 산출물을 재사용하지 않도록 설계돼 있다.

## 구조적 병목

### P0-1. 새 아키텍처가 실제 실행 경로에 채택되지 않았다

기본 CLI `career-pipeline`에는 공고·프로필·자격·발견·지원·감사 명령이 있지만 `run` 또는 `golden` 명령이 없다. 골든패스는 `career-pipeline-golden`이라는 별도 콘솔 스크립트와 별도 모듈로 존재한다. 시스템 벤치마크도 별도 스크립트다.

과거 실행 68건의 관찰값은 다음과 같다.

| 항목 | 건수 |
| --- | ---: |
| 전체 `run.json` 실행 | 68 |
| `quality_mode=v2` | 56 |
| `strict_quality=true` | 56 |
| 공식 연구 | 37 |
| 초안 | 31 |
| 최종 매니페스트 | 27 |
| 레거시 면접팩 | 29 |

주요 상태는 `blocked_posting` 17건, `complete` 15건, `blocked_selection` 14건, `ready_for_research` 8건이었다. 주요 차단 코드는 `missing_posting_questions` 9건, `invalid_posting_source` 5건, `missing_relevant_match` 4건, `question_prompt_mismatch` 4건이었다.

해석은 분명하다. 새 기능의 테스트 통과와 실제 운영 사용 사이에 간극이 있다. 이를 해소하지 않고 더 많은 모듈을 추가하면 경로는 더 분산된다.

### P0-2. 자격 판정기는 정교하지만 실제 입력 경로가 빈다

`eligibility.py`는 학력 수준, 졸업예정일, 경력기간 중복, 자격증 유효기간, 지역 인재 유형을 판정한다. 그러나 실제 입력 생성은 다음과 같이 단절돼 있다.

- 경험 원장에서 `ApplicantProfile`을 만들 때 학력, 자격증, 지역은 항상 빈 튜플로 설정된다.
- 공고 분석에서 `PostingRecord`를 만들 때 모든 필수·우대 조건은 `kind=custom`, `parse_status=manual_review`가 된다.
- 공고 게시일과 마감일도 이 투영 경로에서는 `None`이다.
- 테스트의 세밀한 자격 판정은 사람이 직접 구조화한 `ApplicantProfile`과 `PostingRecord` fixture를 사용한다. 공고 분석→구조화 규칙→자격 판정의 통합 테스트는 없다.

그 결과 실제 경로에서는 자동 판정기가 대부분 `manual_review`에 머무를 수밖에 없다. 해결책은 판정 로직을 더 복잡하게 만드는 것이 아니라, 두 개의 승인된 입력 계약을 추가하는 것이다.

1. 경험 원장과 분리되지만 함께 버전 관리되는 `ApplicantFactsLedger`: 학력, 졸업상태, 자격증, 지역, 근무 가능 조건
2. 공고 문장을 `education`, `experience`, `certification`, `location`, `work_authorization`, `custom`으로 구조화하되, 원문·신뢰도·파서 버전·수동 승인 상태를 보존하는 `EligibilityRuleCompiler`

### P0-3. 자료조사 안전장치는 있으나 실행 오케스트레이션이 없다

공식 도메인 제한, SSRF 방지, 리다이렉트와 콘텐츠 검증을 재사용하는 `retrieve_research_source()`가 있다. 하지만 현재 저장소에서 이 함수의 호출자는 없다. 골든패스는 연구 작업공간과 커버리지를 검사할 뿐, 공식 URL 후보를 수집하고 스냅샷과 주장 후보를 만드는 과정을 실행하지 않는다. 연구가 준비되지 않으면 `waiting_for_research`로 멈추고 외부에서 `04_공식근거.json`과 `04_리서치실행.json`을 완성하기를 기다린다.

자동화의 적정 경계는 무제한 웹 크롤링이 아니다. 다음의 승인형 작업 큐가 적절하다.

`연구 슬롯 생성 → 공식 URL 후보 등록 → 안전한 스냅샷 → 주장 후보 추출 → 충돌/시의성 검사 → 사용자 승인 → 공식근거 승격`

### P0-4. 면접팩이 최종본 앞뒤에서 두 번 수동 병목이 된다

골든패스는 초안이 만들어진 뒤 `08_면접대비팩.md`가 없으면 멈춘다. 최종화로 답변이 바뀌었는데 면접팩이 그대로면 다시 멈춰 새로 작성하도록 요구한다. 그 뒤에야 최종본 기반 `interview_intelligence`를 자동 생성한다.

이 순서는 신선도를 안전하게 지키지만 작업을 중복시킨다. 이미 최종본 기반 주장 그래프와 질문은행 컴파일러가 있으므로 다음과 같이 수렴하는 편이 낫다.

`NRS 초안 → 최종 선택/검증 → 최종본 SHA 확정 → 면접 방어팩·질문은행 자동 초안 → 사용자 검토 → 엄격 검증`

최종화 전에 필요한 것은 완성된 면접팩이 아니라 “각 자기소개서 주장의 방어 가능성 검사”다. 이는 구조화된 claim-defense preflight로 대체할 수 있다.

### P1-1. 시스템 벤치마크가 좁고 골든패스에 연결되지 않았다

현재 시스템 벤치마크는 문항별 답변에 다음 네 변이를 적용한다.

- 지원되지 않은 수치 삽입
- 개인 소유권 확대
- 공백 변화
- 문장 순서 변화

방향은 타당하지만 실제 시스템 불변성을 주장하기에는 범위가 좁다. 전용 `test_system_benchmark.py`도 없고, 과거 실행 산출물도 0건이며, 골든패스 완료 조건에도 포함되지 않는다.

확장 시에는 다음 축이 필요하다.

- 행위자·팀 성과·관찰 결과의 다양한 한국어 표현
- 날짜·단위·퍼센트·총량/부분량 변형
- 공고 질문 교체, 순서 교체, 글자 수 모드 변경
- 오래된 연구·최종본·면접팩 SHA 재사용
- 정상적인 조사 이동, 문단 재배열, 주어 생략에 대한 불변성
- NRS 후보 선택과 대체 경로의 동일 사실 계약

### P1-2. 품질 신호가 실행별로 연결되지 않는다

NRS holdout, 문체 선호, 면접 약점, 최종 품질 감사가 각각 존재하지만 실제 지원 단위의 하나의 평가 원장으로 연결되지 않는다. 따라서 “어떤 사실 계약·전략·NRS 경로·사용자 수정이 어떤 면접 약점과 연결됐는가”를 재현하기 어렵다.

평가 원장은 다음만 저장해야 한다.

- 실행·문항·산출물 SHA와 작성기 설정 해시
- 후보 간 선호와 선택 이유
- 사용자가 최종적으로 수정한 문장 유형과 사실 변경 여부
- 모의면접 차원별 집계 점수와 반복 약점
- 감사 결과와 차단 코드

실제 채용 결과는 기록할 수 있지만 합격 확률 학습의 정답으로 사용하지 않는다. 표본이 작고 기관·직무·경쟁률·시장 시점이 섞이기 때문이다.

## 목표 아키텍처

단일 실행은 다음 상태 기계로 수렴한다.

```text
공식 공고 스냅샷
  → 문항·분량·업무·자격요건 구조화 및 승인
  → 지원자 사실 원장과 자격 판정
  → 공고-경험 매칭
  → 공식 자료조사 작업 큐와 주장 승인
  → NRS v2 후보 생성·장르/사실 게이트·blind 선택
  → 최종 선택·후처리·SHA 확정
  → 면접 방어팩·질문은행 자동 컴파일 및 사용자 검토
  → 시스템 불변성 벤치마크·최종 감사
  → 패키지 검토·사용자 명시 승인
```

각 단계는 네 가지를 공통으로 가져야 한다.

1. 입력 SHA와 파서/모델/전략 버전
2. 사람이 승인해야 하는 항목과 자동 판정 항목의 분리
3. 차단 사유 코드와 한 개의 구체적인 다음 행동
4. 이전 산출물을 덮어쓰지 않는 콘텐츠 주소형 출력

## 구현 순서

### 1단계 — 운영 수렴 패키지

상태: 2026-08-30 구현 완료. 실제 공식 공고를 사용한 production smoke run은 아직 수행하지 않았습니다.

범위:

- 기본 `career-pipeline` CLI에 `run`, `resume`, `status`로 수렴된 골든패스 연결
- 기존 68개 실행을 수정하지 않고 새 계약 준비도를 보고하는 `migrate-plan`
- 상태 출력에 현재 단계, 차단 코드, 필요한 사용자 행동, 입력/출력 SHA를 한 화면으로 제공
- 시스템 벤치마크를 선택적 preflight로 호출할 수 있게 연결

완료 기준:

- 새 strict V2 실행은 별도 모듈 명령을 알지 않아도 골든패스에 진입한다.
- 레거시 실행에 대해 변경 없이 누락 산출물과 재개 가능 여부를 보고한다.
- 기존 CLI 호환성을 깨뜨리지 않는다.
- 관련 테스트와 전체 테스트가 통과한다.

#### 1단계 구현 계약

첫 구현 티켓은 아래 계약으로 고정한다. 구현자는 추가 제품 결정을 추측하지 않고 이 범위에서 시작할 수 있다.

**진입점과 호환성**

- 수정 진입점은 `career_pipeline/__main__.py::build_parser()`와 `main()`이다.
- 새 명령은 기존 최상위 `status --input`과 충돌하지 않도록 `career-pipeline workflow` 그룹 아래 둔다.
- 하위 명령은 `start`, `resume`, `status`, `migrate-plan` 네 개다.
- 기존 `career-pipeline-golden` 콘솔 스크립트와 현재 모든 최상위 명령은 그대로 유지한다.
- `workflow start/resume`는 새 오케스트레이터를 복제하지 않고 `career_pipeline.golden_path_converged`의 실행 경로에 위임한다.

**명령 계약**

```text
career-pipeline workflow start
  --workspace PATH --target TEXT --draft PATH --posting SOURCE --profile PATH
  [--run-name TEXT] [기존 golden writer/finalize 옵션]

career-pipeline workflow resume
  --run PATH [기존 golden writer/finalize 옵션]

career-pipeline workflow status
  --run PATH [--format human|json]

career-pipeline workflow migrate-plan
  --runs-root PATH [--format human|json]
```

- `start`와 `resume`의 옵션 기본값 및 종료 코드는 기존 `golden_path.py`와 동일하게 유지한다: 완료 `0`, 사용자 작업 대기·검토 필요 `2`, 파이프라인 차단 `3`, 잘못된 입력은 기존 CLI 오류 규칙을 따른다.
- `status`는 읽기 전용이다. `13_골든패스.json`과 `run.json`을 읽어 `status`, `next_action`, `run_dir`, `current_stage`, `blocker_codes`, `input_sha256`, `output_sha256`를 반환한다. 완료는 `0`, 그 외 정상 조회는 `2`, 읽을 수 없는 입력은 오류로 처리한다.
- `migrate-plan`은 읽기 전용이다. `--runs-root` 바로 아래의 `run.json` 보유 디렉터리만 스캔하고 어떤 파일도 만들거나 변경하지 않는다.

**레거시 준비도 판정**

- `quality_mode == "v2"`이고 `strict_quality is true`이며 `root`가 존재하고 실행 디렉터리가 그 private workspace의 `career_runs` 아래에 있을 때만 `resume_candidate`다.
- 위 조건이 아니면 `incompatible`로 표시하고 정확한 이유 코드를 반환한다.
- 각 실행에 대해 최신 계약 산출물의 존재와 SHA를 읽는다: 공고 분석, 확정 경험 원장, 매칭, 연구 6종, 초안, NRS 선택, 최종 매니페스트, 레거시 면접팩, 면접지능, 골든패스, 시스템 벤치마크.
- 재개 가능성은 파일 존재만으로 완료를 추정하지 않는다. `resume_candidate`는 “골든패스 preflight를 실행할 수 있음”만 뜻하며, 실제 `resume`이 연구·면접·감사 게이트를 다시 판정한다.
- 결과 스키마는 `career-pipeline-workflow-migration-plan-v1`로 고정하고, 실행별 `run_dir`, `classification`, `reason_codes`, `present_artifacts`, `missing_artifacts`, `recommended_command`를 반환한다.

**시스템 벤치마크 경계**

- 첫 티켓에서는 벤치마크를 완료 차단 게이트로 승격하지 않는다.
- `workflow resume`에 `--system-benchmark off|report|required`를 추가하며 기본값은 `off`다.
- `report`는 최종본과 권한 입력이 존재할 때 보고서를 만들되 점수가 낮아도 골든패스 결과를 바꾸지 않는다.
- `required`는 벤치마크 실행 불가 또는 기존 임계값 미달 시 `review_required`로 끝낸다.
- 전용 테스트가 생기기 전에는 기본값을 `required`로 바꾸지 않는다.

**새 테스트**

- `tests/test_workflow_cli.py`: 기존 `status --input` 비회귀, workflow 위임 인자, 종료 코드, human/JSON 출력
- `tests/test_migration_plan.py`: 읽기 전용 보장, strict V2 판정, workspace 경계, 누락 산출물, 손상된 JSON, 결정적 정렬
- `tests/test_system_benchmark.py`: 네 변이의 안전/불변성, report/required 모드 경계
- 기존 `tests/test_cli.py`, `tests/test_golden_path.py`, `tests/test_golden_path_acceptance.py`와 전체 `pytest`를 함께 실행

**첫 production smoke run 준비 조건**

- 사용자가 선택한 현재 유효한 공식 공고 원문 또는 URL
- 확정 경험 원장과 별도 프로필 파일
- 공고 문항·분량·업무·자격요건 preflight 통과
- 공식 연구 출처의 사용자 승인
- 외부 지원서 제출은 수행하지 않으며, 로컬 최종 산출물과 면접팩 생성까지만 범위에 포함

### 2단계 — 자격검증 입력 수렴

범위:

- 승인형 지원자 사실 원장
- 공고 자격요건 구조화 컴파일러
- 원문·규칙·판정의 추적 가능성
- 공고 분석→프로필→자격 판정 통합 테스트

완료 기준:

- 구조화 가능한 공고 요건은 실제 평가기에서 판정된다.
- 모호한 요건은 이유 코드와 원문을 보존한 채 `manual_review`가 된다.
- 학력·자격증·지역 정보는 경험 원장에 억지로 넣지 않고 별도 권한 원장에서 승인된다.

### 3단계 — 연구와 면접의 수동 경계 축소

범위:

- 공식 자료조사 승인형 작업 큐
- 최종본 기반 면접 방어팩 자동 초안
- prefinal 면접팩을 claim-defense preflight로 대체
- 모의면접 세션 평가와 약점 프로필 연결

완료 기준:

- 연구와 면접 단계가 “파일을 직접 만들어 넣으라”는 지시로 멈추지 않는다.
- 외부 사실과 개인 사실의 승인 권한은 유지된다.
- 최종본 변경 시 면접 산출물이 자동으로 무효화되고 재생성된다.

### 4단계 — 실제 사용 학습과 회귀평가

범위:

- 실행별 평가 원장
- 실제 새 공고 NRS production smoke run
- 확장된 시스템 불변성 fixture
- 기관·직무 유형별 면접 포맷 플러그인

완료 기준:

- 사용자 수정과 선호가 다음 작성의 진단 입력으로 재사용된다.
- 사실 권한을 확대하지 않고 문체·구조 선호만 학습한다.
- 한 번의 전체 회귀로 공고·자격·연구·작성·면접·감사의 핵심 계약을 검증한다.

## 지금 바로 할 작업

다음 구현은 **1단계 운영 수렴 패키지**다. 구체적으로 기본 CLI에 골든패스를 연결하고, 과거 실행을 읽기만 하는 `migrate-plan`을 추가한 뒤, 최신 계약으로 실제 공고 한 건을 끝까지 실행할 준비 상태를 만든다.

NRS 문체를 더 조정하는 작업은 그 다음이다. 현재 NRS는 코드와 회귀평가에서는 기본값이지만 실운영 사용 표본이 0건이므로, 먼저 실제 경로에서 생산 산출물을 만들어야 어떤 추가 문체 개선이 필요한지 근거를 얻을 수 있다.

## 확인하지 못한 사항

- 새 공식 채용공고 한 건을 대상으로 한 실제 NRS 골든패스 완료
- 다른 브랜치 또는 원격 GitHub와 현재 체크아웃의 일치 여부
- 실제 모의면접 세션을 통한 적응형 질문 선택과 약점 갱신
- 확장 시스템 벤치마크의 실제 오탐·미탐률
